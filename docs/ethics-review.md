# การทบทวนด้านจริยธรรมซอฟต์แวร์และ AI (Ethics Review)
## โครงการ: Inventory System (ระบบจัดการคลังสินค้า)
**อ้างอิง:** บทเรียนวิชา Software Engineering in AI Era (บทที่ 14 §14.4.13)

---

## 1. บริบทของระบบและผู้มีส่วนได้ส่วนเสีย (System Context & Stakeholders)

### 1.1 วัตถุประสงค์และขอบเขตของระบบ
ระบบ Inventory System เป็นระบบจัดการสินค้าคงคลังที่ช่วยพนักงานบันทึกการรับ/จ่ายสินค้า คำนวณมูลค่าสต็อก และมีระบบแจ้งเตือนสต็อกต่ำไปยังผู้จัดการผ่าน Email/SMS รวมถึงมีฟังก์ชัน AI ผู้ช่วยวิเคราะห์สต็อกสินค้า

### 1.2 ผู้มีส่วนได้ส่วนเสีย (Stakeholders)
1. **พนักงานคลังสินค้า (Warehouse Operators):** ผู้ใช้งานหน้างานโดยตรง ต้องไม่ถูกระบบสร้างภาระหรือถูกเฝ้าจับผิดการทำงานอย่างไม่เป็นธรรม
2. **ผู้จัดการคลังสินค้าและฝ่ายบริหาร (Managers & Executives):** ผู้รับข้อมูลแจ้งเตือนและรายงานเพื่อตัดสินใจสั่งซื้อสินค้าและวางแผนงบประมาณ
3. **คู่ค้าและซัพพลายเออร์ (Suppliers):** ได้รับผลกระทบจากความแม่นยำของคำสั่งซื้อและช่วงเวลาการเติมสต็อก
4. **ลูกค้าปลายทาง (End Customers):** ได้รับผลกระทบจากความพร้อมของสินค้า หากสต็อกผิดพลาดอาจทำให้เกิดสินค้าขาดตลาด
5. **ทีมผู้พัฒนาระบบ (Development Team):** ผู้รับผิดชอบความถูกต้อง ความปลอดภัย และจริยธรรมของโค้ดที่สร้างขึ้น

## 2. การวิเคราะห์ความเสี่ยงและผลกระทบ (Risk & Impact Analysis)

| กิจกรรม / ข้อมูลที่มีความเสี่ยง | ผู้ที่ได้รับผลกระทบ | ผลกระทบที่อาจเกิดขึ้น (Impact) | ระดับความรุนแรง |
|---|---|---|---|
| **การแจ้งเตือนสต็อกผิดพลาด (False Alarm / Missed Alert)** | ผู้จัดการ และบริษัท | สินค้าขาดสต็อกจนธุรกิจหยุดชะงัก หรือสั่งซื้อสินค้าซ้ำซ้อนจนเกิด Overstock จมทุน | สูง |
| **ข้อมูลส่วนบุคคลรั่วไหล (PII Leakage)** | ผู้จัดการและพนักงาน | เบอร์โทรศัพท์และอีเมลในระบบ Notification รั่วไหลสู่สาธารณะ หรือถูกส่งไปยัง Cloud LLM | สูง |
| **การคำนวณมูลค่าสต็อกคลาดเคลื่อน** | ฝ่ายบัญชีและการเงิน | งบการเงินไม่ถูกต้อง อาจมีความผิดทางกฎหมายหรือเสียภาษีผิดพลาด | สูงมาก |
| **Prompt Injection / คำสั่งไม่พึงประสงค์ผ่าน AI** | ระบบและฐานข้อมูล | ผู้ไม่หวังดีป้อนคำสั่งหลอกให้ระบบลบข้อมูล หรือเปิดเผยข้อมูลสต็อกแก่บุคคลภายนอก | สูง |

## 3. การตอบ 5 คำถามด้านจริยธรรม (Five Ethical Inquiries - §14.4.13)

### คำถามที่ 1: ความเป็นธรรมและการไม่เลือกปฏิบัติ (Fairness & Non-Discrimination)
- **การวิเคราะห์:** กฎเกณฑ์การจัดสรรสต็อกและการแจ้งเตือนต้องอิงตามข้อมูลจริงและตัวเลขทางคณิตศาสตร์ที่โปร่งใส ไม่เลือกปฏิบัติตามหมวดหมู่หรือกลุ่มผู้ใช้ กฎส่วนลดในโมดูลการขายต้องถูกกำหนดเป็นนโยบายมาตรฐาน ไม่มีการลำเอียงราคาหรือผลประโยชน์แอบแฝง
- **ผลกระทบจริง:** ป้องกันความขัดแย้งในการเบิกจ่ายสินค้าและการประเมินประสิทธิภาพของพนักงานในแต่ละกะ

### คำถามที่ 2: ความโปร่งใสและความสามารถในการอธิบายได้ (Transparency & Explainability)
- **การวิเคราะห์:** ทุกครั้งที่ระบบส่งการแจ้งเตือนสต็อกต่ำ หรือรายงานมูลค่าสินค้า ระบบต้องแสดงที่มาของตัวเลขอย่างชัดเจน (เช่น แจ้งว่าสต็อกเหลือ 8 ชิ้น ซึ่งต่ำกว่าเกณฑ์ 15 ชิ้นที่ผู้จัดการตั้งไว้เมื่อวันที่ใด) ไม่ใช่การแจ้งเตือนลอย ๆ จาก "กล่องดำ" ของ AI
- **ผลกระทบจริง:** ผู้จัดการสามารถตรวจสอบเหตุผลย้อนกลับได้ทันที สร้างความเชื่อมั่นในการบริหารจัดการ

### คำถามที่ 3: ความเป็นส่วนตัวและการคุ้มครองข้อมูล (Privacy & Data Protection)
- **การวิเคราะห์:** ข้อมูลข้อมูลติดต่อ (เบอร์โทรศัพท์, อีเมล) ที่ใช้สำหรับ SMS/Email Notifier ต้องถูกเก็บเป็นความลับเฉพาะภายในระบบ ห้ามนำไปใช้เพื่อวัตถุประสงค์อื่น และ**ห้ามส่งข้อมูลเหล่านี้เข้าไปใน Prompt ของ External Cloud LLM โดยเด็ดขาด**
- **ผลกระทบจริง:** ป้องกันการละเมิด พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล (PDPA) และรักษาความไว้วางใจของบุคลากร

### คำถามที่ 4: ความปลอดภัย ความน่าเชื่อถือ และความรับผิดชอบ (Safety, Reliability & Accountability)
- **การวิเคราะห์:** ใครเป็นผู้รับผิดชอบเมื่อเกิดข้อผิดพลาด? ทีมงานกำหนดว่า **ซอฟต์แวร์และ AI เป็นเพียงเครื่องมือสนับสนุนการตัดสินใจ (Decision Support Tool)** ความรับผิดชอบสูงสุดอยู่ที่มนุษย์ผู้ดูแลและทีมผู้พัฒนาที่มีหน้าที่เขียน Unit Test, Boundary Test และ Characterization Test คลุมระบบให้ครอบคลุม
- **ผลกระทบจริง:** มีกระบวนการบันทึก Audit Log ของทุกธุรกรรม (`StockTransaction`) เพื่อให้สามารถตรวจสอบย้อนหลังได้เสมอว่าใครทำรายการใดเมื่อเวลาใด

### คำถามที่ 5: การควบคุมโดยมนุษย์ (Human Agency & Oversight / Human-in-the-loop)
- **การวิเคราะห์:** ระบบจะไม่ทำการตัดสินใจเชิงนโยบายการเงินหรือการสั่งซื้อภายนอกโดยอัตโนมัติเด็ดขาด ทุกธุรกรรมต้องได้รับการอนุมัติหรือยืนยันจากมนุษย์ก่อนเสมอ
- **ผลกระทบจริง:** ป้องกันความสูญเสียทางการเงินหากโมเดล AI เกิดภาพหลอน (Hallucination) หรือเกิดข้อผิดพลาดในการคำนวณ

## 4. การตัดสินใจของทีม: สิ่งที่เลือกทำและ "สิ่งที่ตัดสินใจไม่ทำ" (What We Decided NOT to Build)

### 4.1 สิ่งที่ตัดสินใจทำ (What We Built)
1. สร้าง **Self-Validation** ในทุกคลาส เพื่อดักจับข้อมูลผิดพลาดตั้งแต่ทางเข้า (ห้ามจำนวนติดลบ, ห้ามชื่อว่างเปล่า)
2. แยกส่วน **Notification Interface** เพื่อให้สามารถสลับหรือปิดกั้นช่องทางส่งข้อความได้ทันทีหากระบบมีปัญหา
3. จัดทำ **Audit Log** บันทึกประวัติการรับ-จ่ายสินค้าพร้อม Timestamp เพื่อความโปร่งใส

### 4.2 สิ่งที่ตัดสินใจ "ไม่ทำ" เพราะผ่าน Ethics Review (What We Decided NOT to Build)
> **กรณีที่ 1: ปฏิเสธการสร้างฟีเจอร์ "สั่งซื้อสินค้าอัตโนมัติไปยังซัพพลายเออร์เมื่อสต็อกต่ำ (Autonomous Auto-Ordering)"**
> - *เหตุผล:* ทีมพิจารณาแล้วว่า หากเซนเซอร์ตรวจนับผิดพลาด หรือ AI วิเคราะห์สต็อกคลาดเคลื่อน การให้ระบบสั่งซื้อสินค้าและทำธุรกรรมการเงินโดยอัตโนมัติจะสร้างความเสียหายทางการเงินอย่างร้ายแรง ทีมจึง**ตัดสินใจไม่สร้างระบบสั่งซื้ออัตโนมัติ** แต่ทำเพียง "การแจ้งเตือนพร้อมร่างคำแนะนำ (Draft Notification)" เพื่อให้ผู้จัดการเป็นผู้อนุมัติขั้นสุดท้ายเสมอ (Human-in-the-Loop)
>
> **กรณีที่ 2: ปฏิเสธการส่งประวัติการทำรายการของพนักงานรายบุคคลเข้า Cloud LLM เพื่อประเมินผลงาน**
> - *เหตุผล:* สุ่มเสี่ยงต่อการละเมิดความเป็นส่วนตัวและการประเมินผลงานที่ไม่เป็นธรรมจากโมเดล AI ที่อาจมีอคติ ทีมจึงจำกัดการวิเคราะห์ของ AI ให้อยู่เฉพาะข้อมูลสินค้าและหมวดหมู่เท่านั้น

## 5. มาตรการลดความเสี่ยง (Risk Mitigation Strategies)

1. **Control:** มี Validation Rule ใน Domain Model ปฏิเสธค่าที่ไม่ถูกต้องในทันที
2. **Fallback:** หาก Cloud LLM ไม่สามารถใช้งานได้ หรือมีปัญหา Rate Limit ระบบจะ Fallback มาใช้ Template-based Message แบบคงที่โดยไม่ทำให้ Core Function หยุดชะงัก
3. **Consent & Disclosure:** ระบุชัดเจนในรายงานว่าข้อความใดเป็นข้อความสรุปที่สร้างโดย AI เพื่อให้ผู้ใช้ทราบล่วงหน้า
4. **Logging & Auditing:** เก็บรหัสธุรกรรม ผู้ทำรายการ และผลลัพธ์ใน Log ภายในระบบ โดยปิดบัง (Mask) ข้อมูลส่วนบุคคล
5. **Prompt Guardrails:** ติดตั้ง Guardrails ป้องกัน Prompt Injection ใน `evals/` ก่อนที่จะนำ Prompt ไปใช้งานจริง

## 6. แบบตรวจความพร้อมด้านจริยธรรม 10 ข้อ (10-Item Ethics Checklist)
ทีมต้องตรวจสอบและยืนยัน Checklist ทั้ง 10 ข้อนี้ก่อนทำการ Commit โค้ดหรือ Deploy ระบบทุกครั้ง:

- [x] **1. No Negative Quantity:** มี Test ยืนยันว่าระบบปฏิเสธจำนวนสินค้าและราคาที่ติดลบอย่างเด็ดขาด
- [x] **2. No Empty Input:** มีการตรวจสอบว่าชื่อสินค้าและข้อมูลสำคัญไม่เป็นค่าว่างเปล่า
- [x] **3. PII Protection:** ไม่มีอีเมลหรือเบอร์โทรศัพท์จริงถูก Hardcode ไว้ในโค้ดหรือหลุดไปใน Git Public History
- [x] **4. Transparent Threshold:** เกณฑ์การแจ้งเตือนสต็อกต่ำสามารถตรวจสอบและแก้ไขโดยผู้จัดการได้ตลอดเวลา
- [x] **5. Audit Trail:** ทุกการรับและจ่ายสินค้ามีการสร้างบันทึกประวัติธุรกรรม (`StockTransaction`)
- [x] **6. Human Oversight:** ระบบไม่มีการสั่งซื้อสินค้าหรือตัดจ่ายเงินภายนอกโดยปราศจากการยืนยันจากมนุษย์
- [x] **7. Safe LLM Integration:** ไม่ส่งข้อมูลความลับ ข้อมูลลูกค้า หรือ API Keys เข้าไปใน Prompt
- [x] **8. Fallback Mechanism:** มีกลไกสำรองเมื่อระบบแจ้งเตือนภายนอกหรือระบบ AI ใช้งานไม่ได้
- [x] **9. Test Coverage Verification:** ฟังก์ชันที่เกี่ยวข้องกับความถูกต้องของสต็อกผ่าน Unit Test 100%
- [x] **10. Clear Documentation:** มีเอกสารระบุข้อจำกัดของระบบและความเสี่ยงอย่างชัดเจนใน Runbook และ Readme
