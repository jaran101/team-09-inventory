## 1. การวิเคราะห์โค้ดทีละเมธอดตามคำถามนำ 4 ข้อ

### (1) เมธอด `batch_sell(orders: dict[str, int]) -> dict[str, int]`

* **Docstring บอกว่าอะไร แล้วโค้ดทำตามนั้นจริงหรือไม่?**
  * *Docstring:* ตัดสต็อกสินค้าหลายรายการพร้อมกัน และคืนค่าสต็อกที่เหลือของแต่ละตัว
  * *ความเป็นจริง:* โค้ดทำไม่ตรงตามที่บอกไว้ครับ เพราะไม่ได้เช็กว่าค่า `amount` ติดลบหรือไม่ (`amount <= 0`) แถมยังไม่ได้ทำเป็น Atomic Operation คือถ้าสั่งหักหลายตัวแล้วรายการหลังๆ พัง ตัวที่หักไปก่อนหน้าก็โดนหักเลย ไม่มีการ Rollback คืนค่าให้
* **ถ้าทำงานสำเร็จไปครึ่งทางแล้วเกิด error จะเหลือ state ค้างไว้แบบไหน?**
  * *ผลกระทบ:* เหลือ state ค้างแบบ **Inconsistent / Partial Cut** คือรายการแรกๆ ใน loop ที่หักผ่านแล้ว สต็อกใน `self._inv` จะลดลงจริง แต่พอลูปถัดไปเจอ Error พ่น Exception ออกมา รายการก่อนหน้าก็ไม่โดนยกเลิก ทำให้ข้อมูลสต็อกคลาดเคลื่อน
* **ถ้ามีสอง thread เรียกพร้อมกัน ค่าที่อ่านมาก่อนยังใช้ได้อยู่หรือไม่?**
  * *ผลกระทบ:* ค่าที่อ่านมาใช้ไม่ได้แล้วครับ (เกิด Race Condition) เพราะไม่มี Lock มาคอยกั้นช่วงเช็กและตัดสต็อก ถ้ามี 2 Thread เข้ามาอ่านสต็อกพร้อมกัน ทั้งคู่จะเห็นว่าของพอ แล้วแย่งกันหักสต็อกจนกลายเป็นติดลบได้เลย
* **ถ้าไม่มีข้อมูลเลย บรรทัดที่มีการหารจะพังหรือไม่?**
  * *ผลกระทบ:* เมธอดนี้ไม่ได้มีการคำนวณการหารครับ

### (2) เมธอด `apply_discount(name: str, percent: float) -> float`

* **Docstring บอกว่าอะไร แล้วโค้ดทำตามนั้นจริงหรือไม่?**
  * *Docstring:* คำนวณราคาสินค้าหลังหักส่วนลดเป็นเปอร์เซ็นต์ (ช่วง 0-100)
  * *ความเป็นจริง:* **ทำไม่ตรงตามข้อกำหนดเรื่อง Boundary ของค่าครับ** เพราะโค้ดไม่ได้เช็กเลยว่า `percent` สั่งมาติดลบ (เช่น `-20`) หรือสั่งเกิน 100 (เช่น `150`) ส่งผลให้ราคาสินค้าอาจจะพุ่งสูงขึ้นหรือกลายเป็นติดลบได้เลย
* **ถ้าทำงานสำเร็จไปครึ่งทางแล้วเกิด error จะเหลือ state ค้างไว้แบบไหน?**
  * *ผลกระทบ:* เมธอดนี้เป็นแค่การคำนวณราคาแล้ว return ค่ากลับ ไม่ได้ไปแก้ไข State หรือตัวแปรข้างในระบบ จึงไม่เหลือ State ค้างไว้
* **ถ้ามีสอง thread เรียกพร้อมกัน ค่าที่อ่านมาก่อนยังใช้ได้อยู่หรือไม่?**
  * *ผลกระทบ:* ค่าอาจจะล้าสมัย (Stale Data) ถ้าโดน Thread อื่นแอบมาเปลี่ยนราคาสินค้าหรือลบสินค้านั้นทิ้งไปตอนที่กำลังคำนวณอยู่
* **ถ้าไม่มีข้อมูลเลย บรรทัดที่มีการหารจะพังหรือไม่?**
  * *ผลกระทบ:* ตรงบรรทัดที่หาร `percent / 100` ใช้เลขคงที่ `100` เป็นตัวหารอยู่แล้ว เลยไม่พังด้วย `ZeroDivisionError` แน่นอนครับ

### (3) เมธอด `restock_bulk(items: dict[str, int]) -> dict[str, int]`

* **Docstring บอกว่าอะไร แล้วโค้ดทำตามนั้นจริงหรือไม่?**
  * *Docstring:* เติมสต็อกสินค้าหลายรายการพร้อมกัน
  * *ความเป็นจริง:* โค้ดทำงานไม่รัดกุมครับ ไม่ได้ตรวจว่า `amount` เป็นค่าติดลบหรือไม่ (เปิดช่องให้ใส่ค่าติดลบเพื่อเนียนลดสต็อกได้) และถ้าใส่ชื่อสินค้าที่ไม่มีในระบบเข้ามา โปรแกรมก็จะ Crash พังกลางทางทันที
* **ถ้าทำงานสำเร็จไปครึ่งทางแล้วเกิด error จะเหลือ state ค้างไว้แบบไหน?**
  * *ผลกระทบ:* เหลือ state ค้างแบบ **Partial Restock** คือรายการก่อนหน้าที่บวกสต็อกไปแล้วก็จะค้างไว้อย่างนั้น ส่วนรายการที่เหลือจะไม่โดนเพิ่ม ทำให้สต็อกในระบบไม่ตรงกับใบรับเข้าจริง
* **ถ้ามีสอง thread เรียกพร้อมกัน ค่าที่อ่านมาก่อนยังใช้ได้อยู่หรือไม่?**
  * *ผลกระทบ:* ใช้ไม่ได้ครับ (Race Condition) เพราะโค้ดดึงค่า `current` มาพักไว้ในตัวแปร local แล้วค่อยเอาไปบวกเพิ่มเพื่อเซฟทับ ถ้ามีอีก Thread มาแก้ไขสต็อกในช่วงเวลาเดียวกัน ค่าที่ Thread นั้นเขียนไปจะถูกเขียนทับหายไปเลย (Lost Update)
* **ถ้าไม่มีข้อมูลเลย บรรทัดที่มีการหารจะพังหรือไม่?**
  * *ผลกระทบ:* เมธอดนี้ไม่ได้มีการคำนวณการหารครับ

### (4) เมธอด `average_unit_value() -> float`

* **Docstring บอกว่าอะไร แล้วโค้ดทำตามนั้นจริงหรือไม่?**
  * *Docstring:* คืนค่าเฉลี่ยราคาสินค้าต่อชิ้นของทั้งคลัง
  * *ความเป็นจริง:* ทำงานไม่ถูกต้องตาม Logic ครับ เพราะโค้ดเอาเอามูลค่ารวมไปหารด้วย "จำนวนประเภทสินค้า" แทนที่จะหารด้วย "จำนวนชิ้นทั้งหมด" แถมถ้าในคลังไม่มีสินค้าเลย โค้ดจะพังทันที
* **ถ้าทำงานสำเร็จไปครึ่งทางแล้วเกิด error จะเหลือ state ค้างไว้แบบไหน?**
  * *ผลกระทบ:* เป็นแค่การอ่านข้อมูลมาคำนวณ (Read-only) ไม่ได้เปลี่ยน State ในระบบครับ
* **ถ้ามีสอง thread เรียกพร้อมกัน ค่าที่อ่านมาก่อนยังใช้ได้อยู่หรือไม่?**
  * *ผลกระทบ:* ถ้ามี Thread อื่นกำลังบวกหรือลบสินค้าใน `_items` ตอนที่เมธอดนี้กำลังวนลูปอ่านค่า อาจจะโดน `RuntimeError: dictionary changed size during iteration` จนโปรแกรมพังได้ครับ
* **ถ้าไม่มีข้อมูลเลย บรรทัดที่มีการหารจะพังหรือไม่?**
  * *ผลกระทบ:* **พังทันทีครับ (Critical)** เกิด `ZeroDivisionError` เพราะถ้าคลังว่างเปล่า `len(self._inv._items)` จะได้ค่าเป็น `0` พอเอาไปเป็นตัวหารในบรรทัด `total_value / total_items` โปรแกรมเลย Crash ทันที

## 2. บันทึก Review Comments สำหรับ Pull Request (ครบ 4 ส่วน)

### Comment 1: `batch_sell` — ขาด Atomicity & Transaction Rollback
* **ตำแหน่ง:** เมธอด `batch_sell` บรรทัดที่ 12–18
* **เหตุผลที่ผิด:** เมธอดไม่มีการ Validate สต็อกของทุกรายการให้ผ่านก่อนตัดจริง และไม่มีตัวจัดการ Rollback ทำให้เวลาเกิด error กลางทาง Transaction จะไม่เป็น Atomic
* **กรณีที่จะพัง (Case & Sample Input):**
  * **สถานะระบบเริ่มต้น:** สินค้า A มีสต็อก `10` ชิ้น, สินค้า B มีสต็อก `2` ชิ้น
  * **Input:** `orders = {"สินค้า A": 5, "สินค้า B": 10}`
  * **พฤติกรรมที่พัง:** พอลูปทำงาน รายการแรกสินค้า A โดนตัดเหลือ `5` ชิ้นเรียบร้อย แต่พอลูปรายการสอง สินค้า B มีแค่ 2 ชิ้น สต็อกไม่พอ จึงเกิด `ValueError` พ่นออกมา การทำงานหยุดทันที แต่สต็อกสินค้า A โดนตัดค้างไปแล้วโดยไม่ได้ Rollback คืนค่า
* **ข้อเสนอแนะในการแก้:** ควรปรับให้ตรวจเช็กสต็อกและจับ `KeyError`/`ValueError` ของทุกรายการให้ผ่านหมดก่อนเริ่มหักจริง หรือใช้ `with self._lock:` ร่วมกับ Context Manager เพื่อสั่ง Rollback คืนค่าสต็อกถ้าเกิด Exception

### Comment 2: `apply_discount` — ขาด Boundary Validation ของเปอร์เซ็นต์ส่วนลด
* **ตำแหน่ง:** เมธอด `apply_discount` บรรทัดที่ 22–25
* **เหตุผลที่ผิด:** ไม่มีการเช็กขอบเขตของพารามิเตอร์ `percent` (Boundary Check) ว่าต้องอยู่ระหว่าง `0` ถึง `100` ตามข้อกำหนด
* **กรณีที่จะพัง (Case & Sample Input):**
  * **เคสที่ 1 (ใส่ส่วนลดติดลบ):** `apply_discount("สายไฟ", -50.0)`  
    * **ผลลัพธ์:** ราคาสินค้ากลายเป็น $200 \times (1 - (-0.5)) = 300$ บาท (กลายเป็นเพิ่มราคาแทนที่จะลด)
  * **เคสที่ 2 (ใส่ส่วนลดเกิน 100%):** `apply_discount("สายไฟ", 150.0)`  
    * **ผลลัพธ์:** ราคาสินค้ากลายเป็น $200 \times (1 - 1.5) = -100$ บาท (ราคาสินค้าติดลบ ร้านขาดทุน)
* **ข้อเสนอแนะในการแก้:** เพิ่ม Guard Clause ดักเช็กค่า `percent` ก่อนคำนวณ ถ้า `not (0 <= percent <= 100)` ให้ `raise ValueError("เปอร์เซ็นต์ส่วนลดต้องอยู่ระหว่าง 0 ถึง 100")`

### Comment 3: `restock_bulk` — เกิด Race Condition สต็อกสูญหายเมื่อทำงานแบบ Concurrent
* **ตำแหน่ง:** เมธอด `restock_bulk` บรรทัดที่ 30–35
* **เหตุผลที่ผิด:** ไปอ่านค่าสต็อกมาพักไว้ในตัวแปร local (`current = ...`) แล้วค่อยเอามาบวกเพิ่มเพื่อเซฟทับ โดยไม่มีการใส่ Thread Lock คุมไว้ ทำให้ Thread-unsafe
* **กรณีที่จะพัง (Case & Sample Input):**
  * **สถานะระบบเริ่มต้น:** สินค้า A มีสต็อก `50` ชิ้น
  * **Thread 1:** เรียก `restock_bulk({"สินค้า A": 10})` -> อ่านได้ `current = 50`
  * **Thread 2 (แทรกเข้ามา):** เรียก `sell("สินค้า A", 5)` -> หักสต็อกเหลือ `45` ชิ้น
  * **Thread 1 (กลับมาทำงานต่อ):** เอาค่าที่อ่านไว้มาบวกแล้วเขียนเซฟทับ `50 + 10 = 60`
  * **ผลลัพธ์ที่พัง:** ผลการขายของ Thread 2 สูญหายไปเลย (Lost Update) สต็อกจริงควรเหลือ `55` แต่โดนเขียนทับเป็น `60`
* **ข้อเสนอแนะในการแก้:** เอา `threading.Lock()` มาครอบทั้งบล็อกการอ่านและเขียนค่า หรือเปลี่ยนไปเรียกเมธอด `restock()` ของคลาส `Inventory` ตรงๆ

---

### Comment 4: `average_unit_value` — เกิด `ZeroDivisionError` เมื่อคลังสินค้าว่างเปล่า
* **ตำแหน่ง:** เมธอด `average_unit_value` บรรทัดที่ 40–43
* **เหตุผลที่ผิด:** ไม่ยอมเช็กค่าตัวหารก่อนเอาไปคำนวณ พอคลังไม่มีสินค้า ตัวหาร `len(self._inv._items)` เลยกลายเป็น `0` ส่งผลให้โปรแกรม Crash
* **กรณีที่จะพัง (Case & Sample Input):**
  * **สถานะระบบเริ่มต้น:** `self._inv._items = {}` (คลังสินค้าเพิ่งสร้างใหม่ ยังไม่มีข้อมูลสินค้า)
  * **Execution:** สั่งเรียก `service.average_unit_value()`
  * **ผลลัพธ์ที่พัง:** เกิด `ZeroDivisionError: division by zero` โปรแกรมพังทันที
* **ข้อเสนอแนะในการแก้:** ใส่เงื่อนไขเช็กก่อนว่า `if not total_items:` หรือ `if total_items == 0:` ให้ `return 0.0` ออกไปเลยเพื่อดักไว้

### คำอธิบายเกณฑ์การจัดหมวดและระดับความรุนแรง

* **หมวดหมู่ (Category):**
  * **correctness:** ข้อผิดพลาดด้าน Logic, คำนวณขอบเขตของค่าผิด (Boundary Condition), ทำงานไม่ตรงตาม Business Requirements รวมถึงปัญหาด้าน Concurrency / Race Condition และ Atomicity ที่ส่งผลให้ข้อมูลสต็อกในระบบไม่ถูกต้อง
* **ระดับความรุนแรง (Severity):**
  * **high:** ปัญหาร้ายแรงที่ส่งผลให้โปรแกรม Crash ทันที (`ZeroDivisionError`) หรือทำให้ข้อมูลสต็อกผิดพลาดร้ายแรง/เกิด Data Race เมื่อมีหลาย Thread เรียกพร้อมกัน
  * **medium:** ปัญหาที่ทำให้คำนวณค่าผิดเพราะขาดการตรวจสอบ Boundary (เช่น ใส่ส่วนลดติดลบ) แม้จะไม่ทำให้โปรแกรม Crash ทันทีแต่ทำให้ข้อมูลผิดพลาด
